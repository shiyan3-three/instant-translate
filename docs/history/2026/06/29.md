#### 1. settings.py 持久化

```python

```

`load()` 和 `save()` 同步处理新字段，读写 settings.json。

#### 2. hotkeys.py 即时重注册

文件：`app/hotkeys.py`

GlobalHotkeyService 新增 `re_register(new_hotkeys: HotkeyMap) -> tuple[bool, str]` 方法。

核心流程：

1. 保存旧的 hotkeys 和 bindings
2. stop() 停止当前注册
3. 用新 hotkeys 构建 bindings
4. start() 尝试注册新快捷键
5. 如果 start() 失败（RegisterHotKey 返回 False = 被占用），恢复旧绑定并重启，返回 (False, 错误信息)
6. 成功则返回 (True, "")

冲突检测依赖 Win32 API `RegisterHotKey` 的返回值——如果快捷键已被其他程序占用，返回 False。

#### 3. main.py 信号链

文件：`app/main.py`

`build_application_context()` 从持久化设置构造 HotkeyMap：

```python
hotkeys=HotkeyMap(
    create_selection=settings.hotkey_create_selection,
    toggle_edit_mode=settings.hotkey_toggle_edit_mode,
)
```

`build_desktop_shell()` 中新增 `_on_hotkeys_save` 闭包，连接信号链：

```
SettingsPage.save_requested(create_key, edit_key)
  → MainWindow.hotkeys_save_requested
  → _on_hotkeys_save:
      hotkeys.re_register(new_map)
      → 成功：settings.save() + 状态栏提示
      → 失败：显示错误信息（旧快捷键仍生效）
```

### 关键设计决策

**为什么用 RegisterHotKey 返回值检测冲突，而不是维护全局占用表？**

RegisterHotKey 是 Win32 API 层面的权威判断——如果另一个程序已经注册了同一个快捷键，RegisterHotKey 必然返回 False。自己维护占用表只能检测应用内部冲突，无法检测外部冲突（如其他软件、系统快捷键）。

**为什么 re_register 先 stop 再 start，而不是先注册新的再注销旧的？**

如果先注册新的，旧快捷键和新快捷键可能短暂共存，导致同一时间两个快捷键都生效。先 stop 再 start 保证任何时刻只有一组快捷键生效。如果新注册失败，恢复旧的即可。

## 任务 2：引用层重构 POC 调研

### 背景

当前引用层直接将原始 MD 文件内容拼接到 system prompt 中，存在两个问题：

1. **无结构**：MD 内容原样塞入，AI 理解效率低
2. **attention dilution**：prompt 过长导致注意力分散，术语遵守度下降

用户提出的新方向：

- thinking 模型将原始 MD 处理为结构化的 compiled-references.md
- 拆分为 Global Rules（始终在 system prompt）和 Glossary（按需关键词匹配注入）
- 利用 KV cache 优化

---

### POC 1：引用层拆分 + 关键词注入

文件：`poc_reference_layer.py`

对比方案：

| 方案 | system prompt | 术语处理 | Token |
|------|--------------|---------|-------|
| A（全量） | 完整 glossary 表格在 system prompt | 模型自行查找 | ~1142 |
| B（拆分） | 只有 Global Rules | 关键词匹配 OCR 文本，命中的术语注入 user message | ~807 |

测试数据：20 个软件工程术语（含平假名读音），8 个测试用例。

验证维度：平假名纯度、括号术语、首尾空格、双空格。

#### 结果

| 指标 | A | B |
|------|---|---|
| 通过率 | 7/8 | 7/8（修正验证 bug 后） |
| 缺失括号术语 | 2 | 5 |
| Token | 1142 | 807（省 29%） |
| 关键词匹配准确率 | - | 100% |

#### 发现的问题

1. **ー 字符误判**：正则 `r"^[あ-ん\s\[\]]+$"` 拒绝了 `ー`（U+30FC，长音符号），导致含 `[でーたべーす]` 等条目的测试被误判失败。修正为 `r"^[あ-んー\s\[\]]+$"`。

2. **括号校验逻辑缺陷**：Test 5 无 SE 术语但验证仍要求括号，导致误判。修正为无匹配术语时 `brackets=True`。

3. **术语注入导致漏翻译**：Test 1 注入了 5 个术语后，模型直接输出术语而非翻译整句。在 POC 2 中通过加强 system prompt 指令修复。

#### 核心结论

拆分方案可行，token 节省 29%，关键词匹配 100% 准确。但术语遵守度有回退（2→5），需要质检机制补强。

### POC 2：多重质检机制

文件：`poc_multi_check.py`

在方案 B 基础上增加三层检查 + 修复：

**第一层：程序化检查（正则/字符串匹配，瞬时，零 API 调用）**

- `check_hiragana_only()`：验证括号内是否全是平假名（含 ー）
- `check_bracket_terms()`：检查匹配到的术语是否都带了 `[假名]` 括号
- `check_edge_spaces()`：首尾多余空格

**第二层：并行 flash 检查（ThreadPoolExecutor，2 线程，~2s）**

- `llm_check_completeness()`：翻译是否完整覆盖原文
- `llm_check_segmentation()`：分词/格式问题
- 均使用非思考模型（thinking disabled），各只看一个方面

**第三层：Fix pass（仅检查报错时触发，~2s）**

- `fix_translation()`：将检测到的问题 + 原文 + 翻译发给 flash 模型修正
- 不报错则跳过

同时改进了 system prompt B，增加明确指令："You must still translate the complete source sentence, not just output the glossary terms"。

#### 结果

| 指标 | A（全量） | B（拆分） | B+C（拆分+质检） |
|------|---------|---------|----------------|
| 通过率 | 7/8 | 7/8 | 7/8 |
| 缺失括号术语 | 2 | 5 | 1 |
| 平均耗时 | 1.78s | 1.62s | 4.03s |
| 触发修复 | - | - | 4/8 |

#### 分析

**C 方案的最大价值是程序化括号检查**——将缺失括号从 5 降到 1，fix pass 在 3/4 触发场景下成功补回括号。这部分零 API 调用、瞬时完成。

**整体通过率未提升**，卡在 Test 5（"今天的会议推迟到下午三点"）——无 SE 术语、问题是双空格，LLM 分词检查未捕获。说明 LLM 语义检查对格式细节不如正则可靠。

**C 的额外开销约 2.4s**（B 的 1.62s 基础上），主要来自 LLM 并行检查（~2s）和 fix pass（~2s，按需触发）。

**深层发现**：B 拆分引入了质量回退（缺失括号 2→5），C 本质上是在修补这个回退。真正的对比应该是 B+C vs A：质量勉强持平（少 1 个缺失术语），换来 29% token 节省，但慢 2.25s。

---

### 质检机制优化方向

基于 POC 2 分析，提出以下优化方向：

1. **程序化能修的就不走 LLM**：括号缺失可直接从 glossary 查到假名并字符串插入，不需要 LLM fix pass。

2. **LLM 检查维度换掉**：当前 completeness 和 segmentation 与程序化检查重叠。应换成程序化覆盖不了的维度：术语语义准确性、语气一致性、内容完整性。

3. **问题从源头减少**：B 缺失 5 个括号 vs A 只缺 2 个，说明 B 的 prompt 对术语遵守不够强。加强 system prompt 指令（如 few-shot 示例）从源头减少问题，比事后修补更有效。

4. **检查条件触发**：短句、无术语的翻译不需要跑完整检查链。只有命中术语或原文超过一定长度时才触发相应检查。

核心思路：能程序化的全程序化（检测 + 修复），LLM 只做语义检查且按需触发，prompt 侧持续减少问题产生。
