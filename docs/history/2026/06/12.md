## 问题诊断：DeepSeek API 返回空翻译

### 现象
- API 频繁返回 "API returned an empty translation"
- 有时输出中文推理过程，不是翻译结果
- 选择框内容变化后翻译停止

### 根本原因
1. **DeepSeek Thinking 行为不稳定**：content 经常为空，只有 reasoning_content
2. **Agent Messages 累积**：对话越长，模型越困惑
3. **Prompt 约束冲突**：平假名约束 vs 实际输入（英文+数字+符号）
4. **错误的 Fallback**：当 content 为空时，读取 reasoning_content（推理过程）

### 提出的解决方案
1. **方案 1**：移除 reasoning_content fallback（立即）
2. **方案 2**：实现 Agent messages compact，保留最近 5 轮（根本）
3. **方案 3**：简化或修改 prompt 约束（治标）
4. **方案 4**：关闭 thinking 模式（最后手段）

### 需要 Oracle 评审的问题
1. DeepSeek thinking 是否适合 Agent 持久化会话？
2. Prompt 约束的最佳表达方式？
3. Messages compact 的最佳策略（保留多少轮？术语提取？）

## 测试结果：问题未解决

### 测试发现
应用启动后，所有翻译都返回 `content=(empty)`。

**日志证据**（`logs/debug/2026/06/12-7.log`）：
```
19:58:24 | DEBUG | content preview: (empty)
19:58:25 | DEBUG | content preview: (empty)
19:58:50 | DEBUG | content preview: (empty)
```

### 根本原因（重新分析）

**不是 messages 累积问题**（第一轮就失败）

**真正原因**：
1. 输入文本过于混乱（OCR 错误 + 中英数混合 + 符号）
2. 约束"只能平假名" + 冲突处理"英文数字原样保留" = 矛盾指令
3. DeepSeek 过度思考如何处理矛盾 → 最终忘记输出

**证据**：
Reasoning 显示模型理解了冲突处理指令，但在思考如何应用时卡住了。

### 新的解决方案

已在 `02-专家反馈.md` 中提出 4 个新方案：
- **方案 A**：关闭 thinking（最后手段）
- **方案 B**：放宽约束为条件性（推荐）✅
- **方案 C**：删除平假名约束（简单粗暴）✅
- **方案 D**：分离不同语言对的 prompt（长期）

### 核心矛盾

平假名约束本身和实际使用场景冲突：
- 用户翻译的文本经常包含英文、数字、符号
- "只能平假名"无法处理这些内容
- 即使加冲突处理指令，也会导致模型困惑

### 建议

**立即**：方案 B 或 C（修改/删除约束）
**长期**：方案 D（分离 prompt）
