# 技术选型草案

## 1. 选型原则

本项目的技术选型优先级如下：

- 能稳定实现 Windows 桌面悬浮层
- 能较好支持全局快捷键与系统托盘
- 能较容易进行屏幕区域截图
- 能本地执行 OCR
- 能方便调用 OpenAI 兼容接口
- 便于个人长期维护

## 2. 整体架构建议

推荐采用单机桌面应用架构，不拆前后端服务。

核心原因：

- 本项目主要运行在本地
- OCR、悬浮层、截图和快捷键都强依赖本机能力
- 如果再拆本地前后端，会增加调试复杂度和进程管理成本

推荐结构：

- 桌面应用主进程
- OCR 服务模块
- AI 请求模块
- Prompt 编译模块
- 状态管理模块
- 悬浮层 UI 模块
- GUI 设置模块

## 3. 推荐技术路线

## 方案 A：Python + PySide6

这是目前最推荐的第一版路线。

### 优点

- 做 Windows 桌面 GUI 和悬浮窗比较直接
- 系统托盘、热键、窗口置顶等能力比较成熟
- 调用 OCR、图像处理库方便
- 与 AI HTTP 接口集成自然
- 对个人开发者维护成本较低

### 风险

- 需要较仔细处理高频截图与 UI 更新的线程问题
- 悬浮层细节体验需要打磨

## 方案 B：Tauri + Rust + Web 前端

### 优点

- 包体和性能表现可能更好
- 前端 UI 灵活

### 风险

- 屏幕截图、全局热键、悬浮层细节实现成本更高
- OCR 与本机能力接入会更复杂
- 对当前项目来说，不利于快速进入可用状态

## 方案 C：Electron

### 优点

- UI 开发速度快
- 前端生态丰富

### 风险

- 对这种轻量桌面工具来说偏重
- 内存占用和常驻体验不够理想
- 与系统层能力结合不如 Python 路线顺手

## 4. 推荐结论

第一版推荐采用：

- Python 3.12+
- PySide6
- 本地 OCR 引擎
- OpenAI 兼容 HTTP API

## 5. OCR 相关选型

OCR 是本项目的关键模块之一，选型时应优先考虑：

- 中、日、英三语可用性
- Windows 本地部署难度
- 单次识别延迟
- 结果稳定性

### 可考虑路线

- PaddleOCR
- Tesseract（适合作为对照或兜底，不一定是首选）

### 推荐倾向

优先考虑对中、日、英混合支持更稳定、社区资料更丰富的 OCR 方案。第一版应优先验证：

- 单次区域 OCR 耗时
- 小字、描边字、动态背景下的可用性
- 日文与英文场景的稳定性

## 6. 图像处理

为提升 OCR 成功率，建议加入轻量图像预处理。

可选工具：

- OpenCV
- Pillow

推荐做的预处理：

- 灰度化
- 对比度增强
- 二值化
- 裁边

## 7. AI 接口层

AI 接口层建议采用独立模块封装，负责：

- 读取 GUI 配置
- 读取当前启用的 `compiled prompt`
- 构造 OpenAI 兼容请求
- 执行超时和错误处理
- 做最基础的结果清洗

推荐网络库：

- `httpx`

原因：

- 超时控制清晰
- 异步和同步使用都较方便
- 对后续并发调度更友好

## 8. Prompt 系统模块

由于本项目的翻译行为强依赖 Prompt，因此建议将 Prompt 系统做成独立模块，而不是散落在 GUI 或翻译调用代码里。

该模块建议负责：

- 管理固定模板层
- 保存约束层内容
- 管理知识引用层文档列表
- 提炼知识引用层为术语表、风格规则、固定表达
- 生成 `compiled prompt` 预览
- 保存并启用用户确认后的 `compiled prompt`

推荐数据对象至少包括：

- PromptBaseTemplate
- PromptConstraints
- PromptKnowledgeReference
- PromptKnowledgeSummary
- CompiledPrompt

## 9. 状态管理

每组都需要独立状态，因此建议显式建模。

推荐核心数据对象至少包括：

- GroupConfig
- GroupRuntimeState
- OcrResult
- TranslationTask
- TranslationResult

这样后续调试多组状态时会更清晰。

## 10. 并发与线程建议

本项目至少会涉及以下几类任务：

- GUI 主线程
- 屏幕巡检任务
- OCR 任务
- AI 请求任务

建议原则：

- GUI 更新放主线程
- OCR 与 AI 请求放后台执行
- 每组独立调度，但共享全局资源限制

重点避免：

- 因 AI 请求阻塞 GUI
- 因高频巡检导致 CPU 飙升
- 因多个组同时刷新导致窗口抖动

## 12. 第一版应避免的技术风险

- 一开始就做多平台
- 一开始就接入太多 OCR 引擎
- 一开始就支持太多 AI 服务商的特殊差异
- 一开始就把历史记录、自动语言识别、复杂上下文翻译都塞进去
- 一开始就让运行时翻译动态重编译 Prompt

## 13. 结论

如果目标是尽快做出一个自己会真正用起来的版本，那么技术路线应该偏保守、偏工程实用：

- 用最顺手的桌面技术把悬浮层和交互做稳
- 用本地 OCR 把识别速度控制住
- 用独立 Prompt 编译模块保证 AI 依赖可控
- 用 OpenAI 兼容接口把 AI 翻译做成可替换能力
- 先把一条最短路径做成，再扩展其他能力
