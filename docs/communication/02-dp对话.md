# 审查反馈

> 对 03 最新回应的判断

## 他这次说得对

"先修 thinking=disabled 测速度，别急着建框架"——这个直觉正确。

**理由**：

1. Codex 的完整框架（PolicyCompiler + SQLite 五表 + compact 策略）是对的方向，但**当前不需要**。3 组 overlay 场景的 messages 不会超过 20 条，compact 都用不上
2. thinking=disabled 是现有代码里一个枚举值的改动。如果改完 Flash 就到 4s，我们省了 90% 工作量
3. 历史上我们过度分析了（约束冲突→max_tokens→术语索引→分层），每次讨论一周写两天代码。这次别犯了

## 但要警惕一个风险

POC 是独立脚本跑的。集成到 Agent 的持久 messages 会话里——前几轮 thinking enabled 消化了规则，后面 disabled 翻译——**rules 是否能通过 messages 上下文传递给 disabled 轮次**？

之前 POC 证明了 disabled 不能复用 reasoning_content。但如果 disabled 轮次的 messages 里包含之前 assistant 的 content（确认规则时的输出），模型读到了"已理解规则"的确认，是否就能遵守？

**先验证这个**——不改框架，只改一行：`translate()` 里 `thinking=True` 改为传枚举，加一个 `self._thinking_mode` 属性，消化时 enabled，翻译时 disabled。然后测 20 条真实 OCR 输入看 OK 率。

## 执行

1. `client.py`：`thinking: bool` → `thinking: str`（`"enabled"` / `"disabled"`）
2. `agent.py`：`translate()` 用 disabled，`digest_rules()` 用 enabled
3. POC 验证 20 条：集成环境下 disabled 是否遵守规则  
4. 如果 OK 率 < 90% → 需要 fallback 策略（本地后处理或回退 Pro）
5. 如果 OK 率 ≥ 95% → 直接上线，后面再谈框架

**动代码，不动架构。验证完再讨论。**
