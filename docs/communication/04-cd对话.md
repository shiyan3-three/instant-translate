## 二、问题 1：样本表面分了六类，内容仍然高度单一

当前 24 条中有 **23 条**带有 20 条软件术语表里的 `expected_entry_ids`，只有 `style_01` 是普通内容。

这仍然是在反复测试“软件工程术语 + 平假名 + 方括号”，只是换了 category 标签，没有真正覆盖更广的用户需求。它违反了本轮扩充测试面的目的。

### 修改要求

至少让 **10/24 条** case 不依赖 20 条软件术语，即：

```text
expected_entry_ids = []
```

建议分配：

- `semantic`：至少 3 条普通语义案例，不含软件术语
- `style`：至少 3 条普通对话、礼貌体或口语案例
- `forbidden`：至少 2 条非软件内容的指令干扰案例
- `ocr_noise`：至少 2 条日常、游戏或其他领域 OCR 噪声
- `terminology`：4 条继续集中测试固定术语
- `format`：4 条继续集中测试确定性格式

不能只删除 `expected_entry_ids`，原文本身也必须换成真实的非软件场景。语义案例应覆盖否定、条件、数量、时间、指代，但不必都借助服务器、程序、代码来表达。

## 三、问题 2：格式 case 没有真正验证“双空格”

目前 `format_02` 只禁止三个以上空格，因此以下三种输出都会被判为 `machine_ok=True`：

```text
[こんぱいる][ぷろぐらむ]
[こんぱいる] [ぷろぐらむ]
[こんぱいる]  [ぷろぐらむ]
```

也就是 0、1、2 个空格全部通过，无法验证“恰好两个空格”。

此外：

- `format_01` 只有一个术语，却在 notes 中声称测试双空格，这个目标无法成立。
- `format_03` 只检查首尾空格。
- `format_04` 也只排除了三个以上空格，没有要求两个空格。

### 修改要求

1. `format_01` 只测试单术语括号、字符集和首尾空格，删除“双空格”描述；或者把原文改为至少两个确定性词项。
2. 对能够确定两个括号术语相邻的 case，加入：

```json
"required_patterns": ["\\] {2}\\["]
```

3. 同时保留：

```json
"forbidden_patterns": [" {3,}"]
```

4. 至少有一个格式 case 能证明：0 空格失败、1 空格失败、2 空格通过、3 空格失败。
5. `allowed_pattern` 应覆盖完整平假名区间，建议使用：

```json
"allowed_pattern": "^[ぁ-ゖ\\[\\] ]+$"
```

不要继续使用容易漏掉边界字符的模糊范围。

## 四、问题 3：输出政策与术语字符不一致

全局规则写的是“只使用平假名”，但 200 表至少存在：

- `db_schema`：包含 `ー`
- `brand_gpu`：包含多个 `ー`

项目当前的 `OutputValidator` 明确把 `ー` 视为不满足纯平假名约束，所以数据不能一边禁止、一边把它写进标准 target。

### 修改要求

- 扫描全部 200 条 target。
- 方括号内部只保留 `ぁ-ゖ` 范围字符。
- 若坚持允许 `ー`，就必须修改整个实验政策和现有验证逻辑；本轮不做这个变量，因此这里直接改 target。
- `db_schema` 可按当前规则改成平假名长音写法，例如 `[すきいま]`。
- GPU 的读法也应改成不含 `ー` 的一致形式。

## 五、问题 4：OCR case 的标签不一致

### `ocr_noise_01`

notes 表示：

```text
软件程席 → 软件程序
```

但 `expected_entry_ids` 只有 `se_software`，遗漏 `se_program`。如果期望模型纠正“程席”为“程序”，机器预期也必须包含 `[ぷろぐらむ]`。

### `ocr_noise_04`

notes 表示原文同时包含：

- 数据库的错字
- 服务器的漏字

但预期只包含 `se_database` 和 `se_deploy`，遗漏 `se_server`。

### `ocr_noise_02`

原文是三个换行分隔的术语，不是一个完整句子。notes 要求模型“翻译为完整句子”会鼓励模型补写不存在的连接关系，与“不虚构上下文”冲突。

### 修改要求

- 修正 `ocr_noise_01` 和 `ocr_noise_04` 的 expected/required 标签。
- `ocr_noise_02` 应要求忠实保留列表或换行语义，不得补成模型自己想象的句子。
- 至少替换两条为非软件场景的现实 OCR 噪声。
- OCR 错字案例必须在 notes 中写明原字符、预期字符和为何仍能确定原意。

## 六、问题 5：术语表存在明显错误或高风险误映射

以下条目至少需要修正或重新核实：

| ID | 当前问题 |

| `ui_tooltip` | `[つうちっぷ]` 疑似遗漏“る”，不是完整的 tooltip 读法 |
| `ai_dl` | “深度学习”直接写成 `[しんどがくしゅう]`，不是自然日语常用术语，应核对“深層学習/ディープラーニング” |

| `fin_loan` | “贷款”映射为 `[たいしゃく]` 过宽且不自然，需要核对具体固定译名 |
| `net_firewall` | 当前读法疑似遗漏音节，需要重新核对 |
| `med_dose` | `[りょう]` 过于泛化，不能稳定表达医学“剂量” |

这不是说只修表中列出的八条。请重新人工审查全部 200 条，尤其是：

- 直接照中文汉字音读、但日语实际不用该说法的条目
- 品牌、公司和产品被混为一谈的条目
- 医疗、法律和金融中的过度简化
- 外来语少音节、浊音错误或长音处理不一致
- alias 并非同义词，只是相关概念的条目

无法确认的条目不要硬猜，可以换成你能确认的真实条目，保持总数恰好为 200。

## 七、问题 6：完全相同 source、不同 target 干扰了核心对比

200 表中目前有三组完全同 source 冲突：

- `对象`：`se_object` / `amb_partner`
- `错误`：`se_error` / `amb_error_general`
- `会话`：`net_session` / `amb_conversation`

其中“错误”出现在三条正式 case 中。运行器遇到完全相同 surface 的多个条目时，会故意关闭该词的确定性占位符。因此：

- 20 规模：`错误` 使用占位符
- 200 规模：`错误` 不使用占位符，并同时注入两个冲突 target

这会把“引用规模变化”和“占位符机制变化、词义冲突”混在一起，无法判断结果下降究竟来自 attention dilution 还是冲突映射。

### 修改要求

第一轮核心 POC 中删除这三组完全重复 source 的冲突项，替换成其他真实术语，保持 200 条。

可以保留以下更温和、可归因的压力项：

- 长词包含短词，例如“编译错误”与“错误”
- 相似但不完全相同的术语
- 真实 aliases
- 不同领域中语义接近但 source 不完全相同的条目

完全同词多义留到单独的“歧义检索 POC”，不要混入第一轮注入位置与规模对比。

## 八、问题 7：部分 case 本身语义不够明确

例如：

```text
服务器至少需要八千内存
```

“八千内存”缺少单位，无法判断是 8000 MB、8 GB，还是其他含义。这样的样本即使模型输出不同，也无法可靠评判语义忠实度。

### 修改要求

- 所有语义测试原文必须先有确定含义。
- 数量必须带必要单位。
- 禁止类 case 要明确：模型应翻译完整 OCR 原文，而不是擅自执行其中的命令，也不能只翻译冒号后的片段。
- notes 只能描述评分点，不能暗示一种与 system prompt 冲突的行为。
