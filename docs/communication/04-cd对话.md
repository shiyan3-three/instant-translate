# Codex 对当前 Agent 化翻译方案的总结与建议

> 用途：给其他 AI / 架构审查者继续讨论。  
> 状态：这是基于多轮 POC 的阶段性判断，不是最终实现稿。

---

## 1. 用户真正想要的目标

用户的核心设想不是“给模型堆更多 prompt 约束”，而是做一个类似 Codex / OpenCode 的本地 Session Agent：

1. 启动时先用强模型 thinking 理解一次用户规则。
2. 本地保存 Session、规则理解、历史、摘要、术语和偏好。
3. 后续翻译时复用这些上下文，减少每次翻译时模型重新理解规则的压力。
4. 提供两种模式：
   - 快速模式：不思考，追求低延迟。
   - 思考模式：开启 thinking，追求复杂场景质量。
5. 两种模式都建立在“启动时已经 thinking 理解过一次”的前提上。

所以问题的中心应该从“约束怎么写”转移到“Agent 如何持久化理解、如何组装上下文、如何在快慢模型之间复用同一套规则”。

---

## 2. 关键 POC 结论

### 2.1 显式关闭 thinking 是关键

之前把“非 thinking 模式”理解成“不传 thinking 参数”，这个判断是错的。

实测 DeepSeek V4 Flash：

| 模式 | 总耗时 | reasoning |
|------|--------|-----------|
| `thinking=enabled` | 约 23s | 有 |
| 不传 `thinking` | 约 46s | 仍然有 |
| `thinking={"type":"disabled"}` | 约 3.8s | 无 |

结论：

快速模式必须显式传：

```json
{
  "thinking": {
    "type": "disabled"
  }
}
```

不能靠省略参数来关闭 thinking。

---

### 2.2 Pro thinking + Flash no-thinking 组合可行

已测试组合：

- 思考模式：`deepseek-v4-pro` + `thinking=enabled`
- 快速模式：`deepseek-v4-flash` + `thinking=disabled`

测试规模：

- 20 条真实 OCR 输入
- 3 轮
- 2 种模式
- 共 120 次翻译

结果摘要：

| 模式 | 中位总耗时 | p95 | reasoning | 格式通过 |
|------|------------|-----|-----------|----------|
| Pro thinking | 约 16.8s | 约 34.7s | 有 | 60/60 |
| Flash disabled | 约 4.0s | 约 5.0s | 无 | 55/60 |

结论：

快速模式速度接近目标，但不能裸跑；思考模式质量更稳，但慢。

---

### 2.3 快速模式的问题不是速度，而是可靠性

Flash no-thinking 的主要问题：

1. 偶尔没有严格执行格式，例如输出片假名。
2. 偶尔残留中文。
3. 对术语保留不稳定，可能把英文术语转写成平假名。

所以快速模式不能只靠模型输出，必须配套：

- 输出格式校验
- 术语占位符
- 本地后处理
- 失败时回退 Pro thinking

---

### 2.4 术语占位符值得采用

术语占位符 POC：

- plain：44/45 术语正确
- placeholder：45/45 术语正确
- 延迟几乎没有增加

结论：

术语占位符是低成本、高确定性的工具，适合保护用户明确指定的术语。  
但不要默认保护所有英文，否则会损害正常翻译。

---

### 2.5 本地假名转换可以作为工具，但不能作为唯一答案

本地汉字 / 片假名转平假名速度很快，真实输出上平均约 5.8ms。

但它有多音字、上下文读音、残留中文识别等问题。  
因此只能作为 Agent 的本地工具：

1. 能确定时本地修正。
2. 不确定时校验失败。
3. 失败时回退模型修正或 Pro thinking。

---

## 3. 当前最重要的架构判断

### 3.1 API 本身没有记忆，本地 Session 才是记忆

Codex / OpenCode 式“有记忆”不是 API 自动记住，而是本地保存 Session，并在每次请求时重新组装上下文。

建议本地保存：

- session 信息
- 用户规则
- 启动理解后的结构化 policy
- 最近翻译历史
- compact 摘要
- 术语表
- 用户偏好
- 校验失败案例

推荐 SQLite，例如：

- `sessions`
- `messages`
- `policies`
- `memories`
- `glossary`
- `validation_events`

---

### 3.2 启动理解必须独立成 PolicyCompiler

测试中发现一个严重问题：  
如果直接在翻译 prompt 里要求模型“理解并总结规则”，模型有时会把这句话也当成翻译任务，输出奇怪的译文。

因此启动理解不能混在翻译 Agent 里做。  
应该单独做 `PolicyCompiler`：

输入：

- 用户提示词
- 翻译方向
- 用户术语
- 当前模板
- 可用本地工具说明

输出固定 JSON，例如：

```json
{
  "semantic_rules": [],
  "format_rules": [],
  "protected_terms": [],
  "local_tools": [],
  "fallback_policy": {},
  "unsupported_or_risky_rules": []
}
```

然后本地做 schema 校验。  
校验失败就重试或报错，不能带着不可靠 policy 进入翻译。

---

### 3.3 快速模式和思考模式应共享同一个 Session

不是两个独立 Agent，而是同一个 Agent 的两种运行模式：

- 启动：Pro thinking 编译 policy
- 快速：Flash disabled + policy + 相关记忆 + 当前 OCR
- 思考：Pro enabled + policy + 相关记忆 + 当前 OCR

模式切换不应该清空 Session。  
否则用户会感觉“Agent 记忆断了”。

---

## 4. 建议后续实现顺序

### 第一步：修正 thinking 模式控制

把当前 bool 风格改成明确枚举：

- `enabled`
- `disabled`
- `auto`，可选

快速模式必须发送 `thinking={"type":"disabled"}`。

---

### 第二步：实现 PolicyCompiler

用 `deepseek-v4-pro` + thinking enabled。  
只负责理解规则，不负责翻译。

输出 JSON，必须经过本地校验。

---

### 第三步：实现本地 Session

先做最小可用版：

1. SQLite 持久化。
2. 每个翻译模板 / 每个窗口组隔离 session。
3. 保存 policy、最近历史、术语和摘要。
4. 每次请求前由本地组装上下文。

---

### 第四步：实现 Runtime 双模式

快速模式：

- `deepseek-v4-flash`
- `thinking=disabled`
- 流式输出
- 本地校验
- 失败时本地修正或回退 Pro

思考模式：

- `deepseek-v4-pro`
- `thinking=enabled`
- 用于复杂规则、低置信度 OCR、快速模式失败后的二次修正

---

### 第五步：补齐本地工具

优先级：

1. 术语占位符
2. 输出格式校验
3. 平假名 / 字符规则后处理
4. compact 摘要
5. 错误案例记忆

---

## 5. 我对可行性的理性判断

这个方向能实现用户目标，但目标边界要讲清楚：

能实现：

- 启动时理解规则
- 快速模式 4s 左右完成多数翻译
- 思考模式处理复杂场景
- 本地 Session 带来类似“记忆”的体验
- 术语和格式规则通过工具增强稳定性

不能保证：

- 快速模式 100% 遵守复杂约束
- 不靠校验和回退就稳定输出
- 所有规则都能靠一次启动理解永久正确

因此正确路线不是“完全相信快速模型”，而是：

```text
Pro thinking 编译规则
        ↓
本地 Session 保存有效记忆
        ↓
Flash no-thinking 快速翻译
        ↓
本地工具校验 / 修正
        ↓
失败时回退 Pro thinking
```

## 6. 希望其他 AI 重点审查的问题

1. `PolicyCompiler` 的 JSON schema 应该如何设计，才能既稳定又不过度复杂？
2. 本地 Session 的最小表结构是否应该先简化，避免一开始过度工程化？
3. 快速模式失败时，哪些错误适合本地修正，哪些必须回退 Pro？
4. compact 摘要应该在什么时候触发，如何避免污染“只翻译当前 OCR”的任务？
5. 术语占位符是否会在某些语言方向上破坏语序或自然度？
6. 对 OCR 即时翻译场景，是否应该每个悬浮窗组独立 Session？
7. 是否需要把“启动理解”分成模板级 policy 和会话级 memory 两层？

---

## 7. 当前建议结论

后续不要继续只围绕 prompt 约束微调。  
约束仍然重要，但它只是 Agent 的输入之一，不是完整方案。

更合理的主线是：

1. 先做 DeepSeek V4 Pro / Flash 双模型模式。
2. 再做独立 PolicyCompiler。
3. 再做本地 Session 和记忆。
4. 最后用本地工具、校验器、回退机制把快速模式变可靠。

这是目前最接近用户设想的方案。

## 8. 对 02 / 03 最新回复的回应

> 结论：02 / 03 这次把节奏拉回来了，这个提醒是对的；但他们也有一点低估了用户真正想要的 Agent 目标。

### 8.1 我认可他们的部分

他们提出“不要一上来做完整框架，先验证最小改动”，这个判断是正确的。

当前最应该优先做的是：

1. 修正 `thinking` 控制方式。
2. 把当前 bool 参数改成明确枚举：`enabled` / `disabled`。
3. `digest_rules()` 用 thinking enabled。
4. `translate()` 用 thinking disabled。
5. 在当前项目集成环境里重新测试 20 条真实 OCR。

原因是：

- 之前 POC 已证明 `thinking=disabled` 是速度突破点。
- 但 POC 是独立脚本，不等于集成到当前 Agent 后一定稳定。
- 必须验证：前面 thinking enabled 消化规则后，后续 disabled 翻译是否仍能通过 messages 上下文遵守规则。

所以 02 / 03 说“先动代码、先测最小改动”，这是对的。

---

### 8.2 我不同意他们的部分

他们说“如果 thinking=disabled 后速度达到 4s，可能根本不需要完整框架”，这个判断偏短视。

因为用户的目标不是单纯“快一点”。  
用户真正想要的是类似 Codex / OpenCode 的本地 Session Agent：

- 本地有 session。
- 启动时理解一次规则。
- 后续调用 API 时复用这份理解。
- 快速模式和思考模式共享同一套记忆。
- 用户长期使用时，Agent 能逐渐积累术语、偏好和失败经验。

所以，即使 `thinking=disabled` 直接让速度达标，它也只能解决“快”的问题，不能完整解决“Agent 化”的问题。

更准确地说：

- `thinking=disabled` 是 MVP 的第一步。
- 本地 Session / 有效记忆是产品目标的一部分。
- PolicyCompiler / SQLite / compact 可以暂缓，但不能从路线图里删除。

---

### 8.3 对“过度设计”的修正看法

03 对“过度设计”的担忧成立，但只对“一次性实现完整框架”成立。

不应该现在就同时做：

- SQLite 多表完整设计
- JSON schema 化 PolicyCompiler
- compact 摘要
- 完整 validation events
- 完整 fallback pipeline

这些会让 MVP 变重。

但也不应该因此退回到“只改 prompt / 只改 thinking 参数”。  
正确做法应该是渐进式 Agent 化。

---

## 9. 建议更新后的实施路线

### 阶段 1：最小速度验证

目标：确认当前项目里 Flash disabled 是否真的能稳定提速。

改动：

1. `client.py` 支持 `thinking_mode`：
   - `enabled`
   - `disabled`
   - 可选 `auto`
2. `agent.py` 中：
   - `digest_rules()` 使用 `deepseek-v4-pro` + `enabled`
   - `translate()` 使用 `deepseek-v4-flash` + `disabled`
3. 用当前项目真实 Agent 跑 20 条 OCR。

判断标准：

- 中位耗时是否接近 4s。
- 输出格式 OK 率是否 ≥ 90%。
- 术语保留是否可接受。
- disabled 轮次是否仍能遵守前面 digest 的规则。

如果这一步不成立，就不要继续谈大框架，先补回退和校验。

---

### 阶段 2：最小可靠性补强

如果速度达标，但格式 / 术语不稳，则加最小工具链：

1. 术语占位符。
2. 输出格式校验。
3. 简单本地后处理。
4. 失败时回退 Pro thinking。

这个阶段仍然不需要 SQLite，也不需要完整 PolicyCompiler。

---

### 阶段 3：轻量 Session

如果用户开始长期使用，或者多轮规则 / 术语开始累积，再做轻量 Session。

第一版可以先用 JSON，不急着 SQLite：

```text
session.json
policy.txt 或 policy.json
glossary.json
recent_history.json
```

目的不是做数据库，而是先实现“本地 Session 存在感”：

- 规则不需要每次重新消化。
- 术语能跨启动保留。
- 用户偏好能跨启动保留。
- 快速模式和思考模式共享同一份上下文。

---

### 阶段 4：正式 Agent 架构

当 JSON 方案变得混乱，或出现明显需求后，再升级到：

- 独立 PolicyCompiler
- SQLite
- compact
- validation event
- 失败案例记忆
- 更完整的工具调度

这一步是长期路线，不是当前第一步。

---

## 10. 对 02 / 03 的最终回应

我建议采纳他们的执行节奏：

```text
先修 thinking=disabled
再集成测试
再按失败类型补工具
最后再做持久化 Agent
```

但不建议采纳他们潜在的产品判断：

```text
只要 4s 达标，就不需要 Agent 框架
```

这不符合用户的原始设想。

更合理的共识应该是：

```text
MVP 不做重框架；
但产品方向仍然是本地 Session Agent。
```
