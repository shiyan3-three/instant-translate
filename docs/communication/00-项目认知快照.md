## 1. 产品与目标

| 项 | 内容 |
|----|------|
| 场景 | 直播课/字幕/游戏文字：框选区域 → 持续识别变化 → 翻译显示在附近悬浮窗 |
| 上限 | 最多 **3 组** 独立框选工作流 |
| 原则 | 不打断、低干扰、稳定、速度优先（产品目标约 4s 内，快路径接近；严约束/重试会慢） |
| 架构原则 | 本地 OCR；云端 AI 只做文本；规则/记忆/校验在本地 |

**默认链路**：

```text
快捷键框选 → 500ms 截图 → 变化检测 → OCR →（稳定确认）
→ TranslationService → Agent.translate
→ Fast(thinking=disabled) → 本地 normalize/validate
→（可选）Pro thinking 重试 → UI 悬浮窗
```

### 3.1 必须建立的心智模型

**记忆在本地，不在 API。**

- Profile：按「语言对 + prompt_hash + fast/thinking 模型」准备 Pro bootstrap（通常 3 条消息）
- Session：按 group 存 JSON；**只存可复用 bootstrap**，不把未确认 Flash 译文当长期教条
- 请求上下文：`_messages_for_current_translation` 用 **bootstrap + 当前 OCR**，避免历史 OCR 拼成「汇总翻译」
- 反馈：`FeedbackStore` 用户确认后才注入记忆

**双模：**

| 时机 | 模型角色 | thinking |
|------|----------|----------|
| `digest_rules` / profile 准备 | thinking/Pro | `enabled` |
| 日常 `translate` | fast/Flash | `disabled`（须显式传，省略 ≠ 关闭） |
| 本地校验 hard 失败 | retry/Pro | 可再 `enabled`（贵且慢） |

**DeepSeek 注意：** 不传 `thinking` 不等于关闭；POC 曾测「省略」仍会 reasoning 且更慢。代码应用 `thinking: {"type":"disabled"}`。

### 6.2 当前更该关心的缺陷

**P0**

1. **最坏路径慢**：thinking 重试 / digest 冷启动；要收紧重试条件与预算、保证 profile 预热、超时分层、`path` 日志。  
2. **快 vs 严约束**：本地能修的不要上模型重试；hard/soft 校验；可选质量档位。

**P1–P2**

3. POC 最优策略未全进主链（如部分 retrieved policy / 检索组合）  
4. 实机 checklist（副屏、空 OCR、模型切换、退出清理等）— 见 `history/2026/07/03.md`  
5. 文档与 git：状态文档更新、主题化 commit  

**低**

6. 打包体积、OCR 边缘质量  

### 6.3 代码里已经较好的部分（别重复发明）

- stale 请求 / 两阶段 commit  
- API 槽位 + backoff  
- OCR 锁与预热
