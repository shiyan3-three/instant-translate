# 审查回应

> 对 02-专家反馈.md 的逐项决策

---

## 关于 Messages 膨胀导致 content 为空

### 专家发现

多轮对话后 DeepSeek thinking 模型的 `content` 越来越容易为空（只有 `reasoning_content`，没有实际翻译）。根因：messages 无限增长，模型在约束和输入之间反复纠结。

### 决策

✅ 采纳。方向：messages compact，但不用截断方式。

**保留**：system message + 最近 10 轮原文/译文对
**压缩**：更早的轮次压缩成一段摘要（术语偏好 + 风格倾向）
**常驻**：术语 KV 表（从引用层提取或从翻译中积累）

不做：只保留最后 5 轮（丢失早期术语选择）。

---

## 关于 _extract_content 的 reasoning fallback

### 专家发现

`client.py._extract_content()` 在 content 为空时 fallback 到 `reasoning_content`。但 reasoning_content 是推理过程，不是翻译结果。会把"我们需要将..."这种推理文本显示给用户。

### 决策

✅ 采纳。移除 reasoning_content fallback。content 为空时直接返回空字符串，上层检测并报 TranslationError。

## 关于修改约束（方案 3）

### 专家建议

把"只输出平假名"改为条件性约束——"如果原文只含中文和日文，则只用平假名；如果含英文数字则酌情保留"。

### 决策

❌ 拒绝。问题不在约束严格，在模型不知道遇到不适用约束的内容该怎么处理。应该让 Agent 判断"部分内容不适用该约束，原样保留"，而不是让用户把约束改软。改约束是让用户迁就模型。

---

## 关于关闭 Thinking（方案 4）

### 专家建议

关掉 thinking 模式作为最后手段——避免 thinking 不稳定。

### 决策

❌ 拒绝。POC 已证明关 thinking 不遵守规则。Agent 的核心价值就是 thinking 维持上下文。

## 对执行 AI 三个问题的回应

### 问题 1：方案 2 是否接受分阶段？

✅ 接受。先做简单版 compact（保留最近 10 轮原文/译文对 + system message 永久保留）。

验证效果后：
- 如果 content 为空问题解决了 → 不加摘要，保持简单
- 如果术语一致性有问题 → 再加术语 KV
- 摘要生成作为最后手段，不优先

### 问题 2：约束冲突选 A/B/C 哪个？

✅ 选 **C**。在 Agent 的 system prompt 中加冲突处理指令：

```
当约束与实际输入冲突时，优先保证翻译可用性。
例如：约束要求"只输出平假名"但输入包含英文/数字/符号时，
这些字符原样保留，仅对中文和日文部分应用平假名约束。
```

不选 B——不让用户改约束。不选 A——不能假设 compact 能解决约束冲突，这是两个独立问题。

### 问题 3：简单版 compact 有效后，是否还要加摘要和术语？

看效果决定：
- content 为空问题解决 + 术语一致 → 不加
- content 为空解决但术语不一致 → 只加术语 KV
- content 为空没解决 → 加摘要 + 术语 KV

不做过度设计。先跑简单版看数据。

## 重要发现：thinking deadlock 的根因是约束表述方式

### POC 实测数据（2026-06-12）

四种组合测试（Pro/Flash × thinking开关），每条翻译中文→日语平假名：

| 模型 | thinking | 纯中文 | 混合输入(Team70r) |
|------|:---:|:---:|:---:|
| Pro | True | 0/2 content空 | 0/1 content空 |
| Pro | False | 2/2 ✅ | 0/1 content空 |
| Flash | True | 1/2 | 0/1 content空 |
| Flash | False | 1/2 | 0/1 content空 |

### 根因

不是 thinking 不适合持久会话，不是 messages 膨胀，不是模型选错。是**约束写成了"只能由平假名构成"这种绝对化表述**。模型看到英文/数字时不违反感做不出选择，直接死锁。

日志证据：`reasoning_content` 显示模型在"必须遵守约束"和"输入含有不可转换字符"之间反复纠结。

### 修正方向

Agent 消化规则时不改用户约束，但**检测绝对化表述（只能/必须/绝不），在其后嵌入解除死锁的补充说明**：

```
之前（会死锁）：
"翻译的日语句子只能由平假名构成"

Agent 消化后嵌入补充：
"日语输出使用平假名。英文、数字、符号等无法转换的内容，原文输出。"
```

补充说明不是追加在 system prompt 末尾（会被模型理解为第二条竞争指令），而是紧跟在约束文字后面，作为同一条规则的组成部分。

### Agent 核心不变

- thinking 全程开
- 规则消化一次
- 后续复用 messages
- compact 防溢出
- **新增**：消化时改写绝对化约束，消除死锁条件
