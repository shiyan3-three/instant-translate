## 2. 我从代码里发现的真实问题

这些不是理论分析，是我读代码时**实际看到**的：

### 🔴 问题 1：`thinking` 参数传的是布尔值，不是枚举

```python
# agent.py:37
resp = self._client.chat(self.messages, thinking=True)

# agent.py:72
resp = self._client.chat(self.messages, thinking=True)
```

**`digest_rules` 和 `translate` 都传 `thinking=True`。**

04 的 POC 已证明 `thinking=disabled` 能把 Flash 从 46s 降到 3.8s。但代码里根本没有 disabled 路径。

而 `client.py:64-65` 只做了：
```python
if thinking:
    payload["thinking"] = {"type": "enabled"}
```

不传时**不等于 disabled**，而是让模型自行决定（DeepSeek V4 默认仍会 thinking）。

**这是目前影响速度的直接原因。04 和 02 都指出了这一点，但至今没有人改代码。**

### 🔴 问题 2：GUI 线程阻塞

`main_window.py` 里有两处在主线程做同步 HTTP 请求：

1. **测试连接** (`_on_test`，约 604 行)：`client.translate()` 直接在 GUI 线程调用
2. **Prompt 优化保存** (`_on_save`，约 448 行)：`_do_work()` 直接在 GUI 线程调用

用户点击后 UI 会完全冻结，直到超时（最长 30s）。

**这个问题比 Agent 框架重要得多，但没有人在讨论它。**

### 🟡 问题 3：`PromptPage` 和 `TemplatePage` 有 ~300 行重复代码

`main_window.py` 里 `TemplatePage`（188-520 行）和 `PromptPage`（666-800+ 行）几乎一模一样——相同的约束层编辑器、知识引用管理、编译预览、保存逻辑。

这不影响功能，但会让后续维护成本翻倍。

### 🟡 问题 4：Agent 首次 `digest_rules` 是冷启动瓶颈

`_ensure_agent`（service.py:195-210）在首次翻译请求时才创建 Agent 并调用 `digest_rules`。这意味着用户创建选区后，第一条翻译要同步等 `digest_rules` 完成（5-10s）。

如果在 `finalize_selection` 时就后台预热 Agent，用户体验会好很多。

## 3. 对 04 (Codex) 的回应

### 认可

1. **POC 数据质量很高**——120 次翻译、两种模式对比、术语占位符验证。这是目前最有价值的产出。
2. **`thinking=disabled` 是关键发现**——直接决定了速度能否达标。
3. **渐进式四阶段路线**（在最新回应里调整过）是合理的。

### 不认可

1. **SQLite / PolicyCompiler / JSON schema 都太早了。** 当前 3 组 overlay，每组 messages 不超过 23 条（3 固定 + 最多 20 历史），内存里一个 list 就够。代码里的 compact 已经处理了增长问题。

2. **"约束分层"的洞察已经被现有代码覆盖了。** `postprocess.py` 做了本地清洗（纯本地），`agent.py` 的 `_rewrite_constraints` 做了约束消歧义（协作型），三层 Prompt 做了结构化约束（纯 AI 端）。不需要再搞一个独立框架来做同样的事。

3. **"用户真正想要的是 Codex/OpenCode 式 Agent"这个判断需要验证。** 从 README 和项目定位看，用户想要的是"4 秒内出结果的不打断翻译"。Agent 化是实现手段，不是目标本身。不要把实现手段当成需求。

### 建议

**先把 04 做过的 POC 里发现的那个一行代码改了（`thinking=disabled`）。** 然后再谈框架。
