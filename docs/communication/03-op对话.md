# 03-op 对话：工程债影响、当前缺陷与解法

> 最后更新：2026-07-11  
> 作者：执行 AI（Sisyphus）  
> 性质：架构/缺陷总结（基于当前 `app/` 代码，非 6 月旧文档）  
> 用途：给项目方 / 其他 AI 对齐「什么可延后、什么现在该修」

---

## 1. 先澄清：这里的「1」和「2」指什么

指的是此前讨论架构代价时提出的两条**结构方案**（可维护性重构，不是功能需求）：

| # | 名称 | 含义 |
|---|------|------|
| **1** | **RenderPlan / 策略收敛** | 一次翻译请求只生成一份不可变计划（policy、引用保护、占位符、term_wrapper_mode、expected_wrapped 等），后续 normalize / validate / 组消息只读这份，不再各推一套 |
| **2** | **拆 `translate` / `service` 管线** | 把巨石路径拆成 prepare → execute → postprocess → retry → commit；`TranslationService` 只编排，策略细节下沉 |

---

## 2. 1 和 2 的影响（重点）

### 2.1 它们影响什么 / 不影响什么

| 维度 | 做 1（RenderPlan） | 做 2（拆管线） |
|------|-------------------|----------------|
| 用户体感速度 | **几乎无直接影响** | **几乎无直接影响** |
| 改规则/术语策略成本 | **明显降低**（少漏改） | 间接有帮助 |
| 可读性 / 可测试性 | 中高 | **高** |
| 新人 / 多 AI 协作 | 中 | **高** |
| 短期交付风险 | 中（要抽对边界） | **偏高**（挪代码面大） |
| 与现有 260+ 测试关系 | 可小步抽、测试锁行为 | 必须测试托底 |

**一句话：1、2 的影响是「工程可维护性」，不是「翻译变快」。**

### 2.2 为什么可以等项目差不多再做

1. 主链路（框选 → OCR → Agent → 校验/重试 → UI）**已经能跑**，不拆也能迭代。  
2. 仓库里已有较完整单测，**成形后再抽**比策略还在变时抽更安全。  
3. 当前用户痛点更可能是：**慢路径、预热、实机边界、策略未收口**——这些不靠大重构解决。  
4. 过早拆管线容易和仍在变的 policy / reference 策略**拆两次**。

### 2.3 延后的代价（要心里有数）

- 改 term_wrapper / 平假名 / 引用规则时，仍要在 `agent.py` 长函数里多处改。  
- 出「偶发特别慢」时，更难一眼区分 fast / retry / digest。  
- 代码审查成本继续升高。  

→ **可延后，不建议永远不做。** 建议节奏：

```text
产品定型 + 快稳可接受
    → 再做 1（RenderPlan）
    → 再做 2（管线拆分）
```

### 2.4 延后期间的轻量护栏（可选，不算大重构）

1. 日志区分路径：`path=fast|retry|digest` + 耗时。  
2. 新逻辑尽量抽私有方法，禁止再复制一套 mode 判断。  
3. 每加一种术语/约束模式，固定 3～5 条 golden 测试。

## 3. 当前项目缺陷（代码层）

### 3.1 高优先级（用户能直接感到）

#### A. 最坏路径仍然很慢

**代码事实：**

- 正常：`thinking="disabled"` 走 fast client。  
- 校验失败（部分原因）：`thinking="enabled"` 重试，retry client timeout 可到 **120s**、`max_tokens` 更大。  
- Profile miss：可能在请求路径上触发 `digest_rules`（Pro 冷启动）。  

**体感：** 平均快路径尚可，**偶发 10s～几十秒** 更伤。

#### B. 快路径 vs 严约束冲突

Flash 在平假名 / 术语包裹 / 空格等规则上不稳 → 本地校验失败 → 触发慢重试 → 又慢又贵。  
这是结构张力，不是单纯「没写 disabled」。

#### C. 策略分散（与「1」相关，但是产品债的表现）

同一套术语/引用语义散落在：

- `ConstraintPolicy` / `policy.py`  
- `ReferenceStore.protect`  
- `TermPlaceholder`  
- `agent` 内 `_term_wrapper_*` 与 runtime 文案  

改一处易漏。

#### D. `translate` / `service` 巨石（与「2」相关）

`agent.translate`、`service._execute/_ensure_agent` 同时承担编排、策略、IO、持久化，难读难测。

---

### 3.2 中优先级

| 缺陷 | 说明 |
|------|------|
| POC 策略未完全进主链 | 双模/占位符/policy/reference/反馈已进主链；部分检索/bootstrap 变体仍主要在 `poc/` |
| 冷启动抖动 | 已有 `prepare_agent_profile`、OCR 预热；配置不全、profile miss、语言切换仍可能同步 digest |
| 实机边界未完全收口 | 副屏、连续拖放、短暂空 OCR、模型切换、退出后台任务、Prompt 路径迁移等需 checklist |
| 文档与仓库 | `current-status.md` 偏旧；工作区大量未提交改动 |

### 3.3 低优先级 / 可观察

- 历史串台观感（代码已限制请求上下文为 bootstrap + 当前 OCR，若仍出现优先查 UI 回调）  
- OCR 噪声与偶发慢  
- 打包体积 ~720MB

## 4. 缺陷对应解决方案

### 4.1 最坏路径慢 — **现在该做（P0）**

| 手段 | 做法 | 预期 |
|------|------|------|
| 收紧重试 | 仅 hard 失败（script 泄漏、中文残留、元推理）才 thinking 重试；separator / 轻微缺术语不重试 | 少进慢路径 |
| 重试预算 | 每组每分钟最多 N 次 thinking（如 2） | 控最坏延迟 |
| 超时分层 | Fast 短超时；Retry 单独上限（如 45–60s），避免默认 120s 常态化 | 失败更快可见 |
| 预热闭环 | 启动 / 改 API·模型 / 改语言后必 `prepare_agent_profile`；UI 显示「规则准备中」 | 降首条尖刺 |
| 观测 | 日志：`path=fast\|retry\|digest` + ms | 用数据改，不靠猜 |

### 4.2 快 vs 严约束 — **现在该做（P0/P1）**

| 层 | 做法 |
|----|------|
| 本地优先 | 片假名→平假名、空格/标点 → 只 normalizer，不升级模型 |
| 校验分级 | hard vs soft（已有 `_can_return_best_effort` / `_should_retry_validation_failure`，补全约定与测试） |
| 产品档位（可选） | `fast` / `balanced` / `strict`，严格模式提示可能更慢 |
| 策略 | 字符级尽量 policy 本地执行；语义级才靠模型 |

### 4.3 策略分散（方案 1）— **项目成形后再做**

1. 引入请求级 `RenderPlan`（或等价 context），一处计算、处处只读。  
2. Term 保护收成 facade：`apply` / `restore`。  
3. 禁止从 system prompt 字符串再猜 mode。  

**影响：可维护性 ↑；速度 ≈ 不变。**

### 4.4 巨石函数（方案 2）— **方案 1 稳住后再做**

```text
prepare → execute_fast → postprocess → maybe_retry → commit
```

- 先行为锁定（现有测试）再挪代码。  
- **影响：可读/可测 ↑；速度 ≈ 不变。**

### 4.5 POC 未全进主链 — **P2，数据驱动**

1. 表：POC 名 → 是否已在 service/agent 调用。  
2. 只集成盲审优于现状的策略。  
3. 可用开关灰度。  

### 4.6 冷启动 / 实机 / 文档仓库 — **P1–P2**

- 配置变更即预热；实机 10 分钟 checklist（对齐 `docs/history/2026/07/03.md`）。  
- 更新 `docs/context/current-status.md`；按主题拆 commit 收口。

## 5. 推荐优先级（在不做大重构 1、2 的前提下）

```text
P0  重试分级 + 重试预算 + path/耗时日志
P0  预热覆盖：启动 / 改配置 / 改语言
P1  本地能修的失败禁止 thinking 重试（补测试）
P1  实机 checklist 一轮
P2  文档与 git 收口
P2  按需集成已验证检索策略
P3  产品定型后 → ① RenderPlan → ② 管线拆分
```

## 6. 代码层面的进度判断（便于对齐）

| 目标 | 约略完成度 |
|------|------------|
| MVP 能用（框选→OCR→翻译→显示） | ~90% |
| Agent 双模 + 校验回退 | ~80–85% |
| 约束本地执行 + 引用保护 | ~70–75% |
| 记忆 / Session（克制版） | ~65–70% |
| 策略最优 + 发布整洁 | ~60–65% |

**一句话：** 功能主链已可用；当前债是「慢路径与策略复杂度 + 文档仓库」；**1/2 是后期工程整理，不是当前阻塞项。**

---

## 7. 明确结论（给决策用）

1. **1（RenderPlan）、2（拆管线）可以等项目差不多再做。**  
2. **它们的影响主要是好维护，不是立刻变快。**  
3. **现在更该做的是：** 收紧 thinking 重试与预算、保证 profile 预热、本地能修不升级模型、实机验收、文档与 git 收口。  
4. **不建议**为提速先上 SQLite 大框架或停功能做两周纯重构。  

---

## 8. 可选的下一步（若要动代码）

最小、高收益、不动大架构的一刀：

- **RetryPolicy 收紧 + 每组重试预算 + `path/耗时` 日志**  
- 半小时～半天量级，用现有测试回归  

1/2 大重构：**待产品与策略稳定后再开。**
