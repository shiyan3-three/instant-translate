# 桌面软件开发与打包路线

## 1. 这份文档解决什么问题

这份文档回答的是一个很实际的问题：

从现在这套 `instant-translate` 项目规划出发，怎样一步一步把它做成一个真正的 Windows 桌面软件，并最终打包成用户可以下载使用的 `.exe`。

重点不是“理论上能不能打包”，而是：

- 先做什么
- 后做什么
- 哪一步才适合开始打包
- 打包时 OCR、AI 配置、资源文件怎么处理

## 2. 最终交付目标

本项目最终希望交付的不是网页，也不是脚本，而是一个标准的 Windows 桌面软件。

目标形态如下：

- 用户下载压缩包或安装包
- 双击启动主程序
- 程序在系统托盘常驻
- 支持全局快捷键
- 支持悬浮选择框与翻译窗
- 支持 GUI 配置 AI 接口和 Prompt 系统
- 最终可作为 `.exe` 运行

## 3. 推荐技术路线

当前推荐路线保持不变：

- Python 3.12+
- PySide6
- 本地 OCR
- OpenAI 兼容 AI 接口
- PyInstaller 作为第一版打包工具

这条路线适合当前项目的原因：

- 能较自然地实现 Windows 桌面窗口、托盘和悬浮层
- 本地图像处理、OCR、HTTP 请求集成简单
- 打包成 `exe` 的资料多，路线成熟
- 对个人项目和开源维护都比较友好

## 4. 开发与打包的正确顺序

一个常见误区是：一开始就想着“怎么打包成 exe”。

对这个项目来说，正确顺序应该是：

1. 先做成能在本机运行的桌面程序
2. 再做成你自己会长期开着用的工具
3. 最后再打包成别人能下载使用的版本

也就是说，`打包` 是交付阶段，不是起步阶段。

## 5. 建议分阶段推进

## 阶段一：做出最小桌面程序

这一阶段先不追求完整功能，只验证“它确实是一款桌面软件”。

最低目标：

- 能启动一个主窗口
- 能最小化到托盘
- 能注册全局快捷键
- 能显示一个置顶的测试悬浮窗

这一阶段的成功标准不是“能翻译”，而是：

- 软件框架跑起来了
- Windows 桌面形态成立了

## 阶段二：做出单组闭环

这一阶段目标是让软件第一次“真工作”。

最低目标：

- 新建一个选择框
- 截图固定区域
- 做 OCR
- 调 AI 接口
- 在翻译窗显示结果

这一阶段完成后，它已经不是“空壳软件”，而是一个最小可用工具。

## 阶段三：补齐正式交互

这一阶段再补：

- 托盘菜单
- GUI 设置窗口
- 3 组独立工作流
- 编辑模式
- Prompt 三层架构
- Prompt 编译预览与确认

## 阶段四：开始考虑打包

只有当前三个阶段都稳定之后，才建议开始正式做打包。

原因很简单：

- 如果程序自己都还不稳定，打包只会放大调试难度
- OCR 和资源文件路径问题在开发期不明显，在打包期会集中爆发

## 6. 为什么第一版推荐 PyInstaller

第一版推荐优先使用 `PyInstaller`。

原因：

- 成熟
- Windows 上使用广泛
- 对 PySide6 支持路线清晰
- 对个人项目足够实用

它不是唯一方案，但很适合第一版。

后续如果你追求更小包体、更强性能或更好的逆向保护，再考虑 `Nuitka` 之类的工具也不迟。

第一版建议不要一开始就上更复杂的打包链。

## 7. 打包前必须先想清楚的 5 件事

## 7.1 配置文件放哪里

你的项目不是纯静态程序，它依赖：

- AI 接口配置
- Prompt 相关文件
- `compiled prompt`
- 可能的 OCR 配置

这些内容不能全都硬编码在程序里。

建议原则：

- 程序本体和用户配置分离
- 用户配置应放在一个固定的本地目录
- GUI 修改配置时，写入该目录

## 7.2 Prompt 文件怎么处理

Prompt 系统里至少有这些内容：

- 固定模板层
- 约束层原始输入
- 知识引用列表
- `compiled prompt`

建议：

- 固定模板层可以跟随程序资源分发
- 约束层和知识引用层属于用户配置
- `compiled prompt` 作为当前启用版本，应该写入本地用户目录

不要把用户正在使用的 `compiled prompt` 只放在临时内存里。

## 7.3 OCR 依赖怎么带

打包的真正难点之一不在 GUI，而在 OCR。

你要提前验证：

- OCR 引擎是否需要额外模型文件
- 模型文件是否需要跟程序一起分发
- 打包后这些文件能否被正确找到

因此在开发期就要尽量避免“路径写死在源码里”。

建议尽早设计：

- 程序资源目录
- 用户配置目录
- OCR 模型目录

## 7.4 截图和悬浮层在打包后是否行为一致

有些程序在开发运行时正常，但打包后：

- 快捷键失效
- 置顶窗行为变化
- 托盘图标异常
- 高 DPI 缩放表现异常

因此打包测试不能只看“程序能不能启动”，而要专门测试：

- 托盘
- 快捷键
- 选择框
- 翻译窗
- 多屏和缩放

## 7.5 日志怎么做

打包后调试会比开发期难，所以建议尽早加最基础的日志机制。

至少记录：

- 程序启动
- 快捷键触发
- 选区创建
- OCR 结果是否为空
- AI 请求是否成功
- Prompt 是否成功加载

这样打包后出问题时，不至于完全靠猜。

## 8. 推荐的目录与资源策略

建议把文件分成三类：

### 1. 程序源码

- 跟随项目仓库
- 参与打包

### 2. 程序资源

- 默认 Prompt 模板
- 图标
- 可能的 OCR 模型或资源文件

### 3. 用户运行时数据

- AI 配置
- 约束层输入
- 知识引用列表
- `compiled prompt`
- 日志

核心原则是：

`程序资源` 和 `用户数据` 分离。

## 9. 推荐的打包节奏

## 第一次打包

第一次打包只验证这些：

- 程序能启动
- 主窗口能打开
- 托盘能显示
- 快捷键可注册

不要一开始就要求：

- OCR 正常
- AI 正常
- 3 组都正常

第一次打包的目的只是证明“桌面应用外壳可以发出去”。

## 第二次打包

验证：

- 单组完整翻译链路
- 配置文件读写
- `compiled prompt` 读写

## 第三次打包

验证：

- 3 组并发
- 编辑模式
- 拖动翻译窗
- 越界避让

## 10. 最终分发形式建议

第一版对外分发可以先采用最简单形式：

- 一个打包好的目录
- 或一个压缩包
- 主程序是 `.exe`

也就是说，第一版不一定马上做安装器。

等稳定之后，再考虑：

- 安装器
- 开始菜单快捷方式
- 桌面快捷方式
- 卸载入口

如果以后要做安装器，可以再考虑 Windows 常见安装方案，比如 Inno Setup 一类工具，但那是第二阶段的交付优化，不是当前核心。

## 11. 开发期你最先应该看到什么

如果路线正确，最先应该看到的不是“翻译对了”，而是这些里程碑：

1. 一个能打开的桌面窗口
2. 一个能缩到托盘的程序
3. 一个能置顶显示的测试悬浮窗
4. 一个能框选区域的选择框
5. 一个能显示测试文本的翻译窗

只要这几个都出来了，你就已经真正进入“软件开发”了。

## 12. 打包前检查清单

准备第一次正式打包前，建议至少确认：

- 主窗口正常
- 托盘正常
- 快捷键正常
- 选择框正常
- 翻译窗正常
- OCR 引擎路径正常
- AI 配置可保存
- `compiled prompt` 可生成、可确认、可读取
- 日志能写出

## 13. 最推荐的近期路线

对你现在来说，最推荐的实际推进顺序是：

1. 先把 `PySide6` 主窗口跑起来
2. 再把托盘和快捷键跑起来
3. 再做一个测试悬浮窗
4. 再做选择框
5. 再接 OCR
6. 再接 AI
7. 再接 Prompt 编译系统
8. 最后再做第一次 `exe` 打包

## 14. 结论

你现在走的技术路线没有问题，而且是适合做成可下载桌面软件的。

需要记住的一句是：

`先把它做成你自己会一直开着用的软件，再把它打包成别人也能下载的 exe。`

这样做，路线会稳很多，也不会一开始就被打包问题拖住。
