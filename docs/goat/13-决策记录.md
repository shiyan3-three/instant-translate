## 2026-07-16 · 网页自动填入：软件 OCR/译文 → 网页输入框

**决策**：做「自动填入网页」能力时：内容只来自本软件 OCR 框与 AI 译文框；用户先在网页选中输入框，再在软件侧用互斥可自关的开关选择 OCR 或译文；**两侧框体都稳定出字后**再写入网页；只写入、不提交表单。实现为桌面状态机 + 本机桥 + 浏览器扩展（详见 `16-网页自动填入插件设计.md`）。

**原因**：
- 用户需要把稳定后的识别/翻译结果灌进网页表单，而不是在网页里重做 OCR。
- 纯网页 JS 无法读取桌面悬浮窗内容，必须桥接。
- 双稳定门槛复用现有 OCR 稳定与译出落窗语义，避免半截字刷进表单。

**替代方案**：仅网页内假数据演示；或点按钮立刻写入不稳定文本。被否决——与真实产品链路不符、易误填。

## 2026-06-03 · 翻译 Agent 化，不单独做后处理层

**决策**：翻译管线改为 Agent 模式，规则在会话开始时一次性消化，后续翻译只发原文。不单独实现本地后处理校验层。

**原因**：
- 本地后处理只能做字符变换（平假名转写、去标点），做不了语义判断（敬体、语气）
- Agent 化后规则在 KV cache 里，思考模型也能秒回，不需要快慢模型切换
- 在 DeepSeek 网页实测中发现：思考模型先思考一次、之后关思考模式也服从，证明 thinking 只需在消化阶段用一次

**替代方案**：后处理层 + 快模型。被否决——字符变换覆盖面太窄，语义约束仍需思考模型。

## 2026-06-03 · 翻译模板合并三个功能

**决策**：侧边栏从四页改为三页，"翻译模板"合并原"翻译方向"+"提示词"+"会话管理"。

**原因**：
- 语言方向、约束层、引用层、会话上下文是同一个翻译场景的不同维度
- 分开管理导致：用户改了语言方向、提示词还在另一个页面；上下文和规则不挂钩
- 合并后一个模板 = 一个完整的翻译场景，切换模板一键切换所有配置

**替代方案**：保持四页不变，Agent 自动关联。被否决——用户需要一个地方看到"这个翻译场景的全部配置"。

## 2026-06-03 · 上下文溢出：本地存储 + compact

**决策**：上下文存本地 JSON，窗口快满时 compact 旧条目为摘要嵌入。

**原因**：
- 纯内存方案重启丢失，纯 API 方案 token 爆炸
- Windsurf 的本地存储 + Cursor 的 compact 压缩是已验证的模式
- 摘要压缩保住了关键信息，不丢术语偏好

**替代方案**：固定窗口 FIFO。被否决——可能丢失用户长期偏好的术语选择。

## 2026-06-03 · 模型配置暂时全局统一

**决策**：不按翻译模板独立配置模型，全局一个模型设置。

**原因**：
- 当前只有一个 API，按模板独立配置的收益不大
- Agent 化后规则消化和翻译都用同一个会话，不需要快慢模型分离
- 未来如果有多 API 需求再拆

**替代方案**：按模板独立。暂缓。

## 2026-06-02 · 穿透用 WS_EX_TRANSPARENT，不用 setMask

**决策**：选择框穿透用 Win32 `SetWindowLongW` 操作 `WS_EX_TRANSPARENT`，编辑模式去掉该标志。

**原因**：
- `setMask` 只留边框时，拖动时鼠标移出边框就丢捕获
- `WindowTransparentForInput` + hide/setWindowFlags/show 切换不可靠
- Win32 直接操作窗口扩展风格是最底层、最可靠的方式

**替代方案**：setMask 边框、WA_TransparentForMouseEvents、nativeEvent WM_NCHITTEST。全部试过，不够稳。

## 2026-06-02 · PaddleOCR 降级到 2.7.3

**决策**：PaddleOCR 从 3.x 降级到 2.7.3，PaddlePaddle 从 3.3.1 降级到 2.6.2。

**原因**：
- PaddleOCR 3.x API 不兼容（use_gpu→取消、ocr()→predict()、cls→取消）
- PaddlePaddle 3.3.1 在 Python 3.9 + Windows 上有 oneDNN PIR 属性 bug（`ConvertPirAttribute2RuntimeAttribute not support`）

**替代方案**：升 Python 3.12+。被否决——优先稳定，不升级环境。
