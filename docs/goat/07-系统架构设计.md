# 系统架构设计

## 1. 设计目标

本项目的系统架构需要同时满足以下目标：

- 支持 Windows 本地桌面悬浮交互
- 保持 OCR、Prompt 编译和 AI 翻译职责分离
- 支持最多 3 组独立的识别与翻译工作流
- 让运行时翻译尽量短路径，减少额外阻塞
- 让 Prompt 三层架构成为系统中的正式模块，而不是零散配置

## 2. 总体架构

推荐采用单进程桌面应用架构，以本地应用为核心，不拆分本地前后端。

整体链路如下：

`全局快捷键 / GUI -> 选择框与翻译窗 -> 区域截图与变化检测 -> OCR -> 文本清洗 -> compiled prompt + AI 翻译 -> UI 刷新`

## 3. 模块划分

## 3.1 GUI 模块

职责：

- 提供设置窗口
- 提供主配置入口
- 承担 Prompt 配置与编译预览界面
- 提供托盘操作入口

对应目录：

- `app/gui/`

## 3.2 Overlay 模块

职责：

- 绘制选择框
- 绘制翻译窗
- 管理编辑模式
- 控制工具条显示与隐藏

对应目录：

- `app/overlay/`

## 3.3 Capture 模块

职责：

- 按组进行固定区域截图
- 执行区域变化检测
- 为 OCR 提供原始图像输入

对应目录：

- `app/capture/`

## 3.4 OCR 模块

职责：

- 执行图像预处理
- 调用 OCR 引擎
- 输出文本和基础元信息

对应目录：

- `app/ocr/`

## 3.5 Prompt 模块

职责：

- 管理固定模板层
- 管理约束层与知识引用层
- 生成 `compiled prompt` 预览
- 保存用户确认后的 `compiled prompt`
- 为翻译模块提供当前启用版本

对应目录：

- `app/prompt/`

## 3.6 Translation 模块

职责：

- 读取当前 AI 配置
- 读取当前启用的 `compiled prompt`
- 调用 OpenAI 兼容接口
- 返回纯翻译文本

对应目录：

- `app/translation/`

## 3.7 State 模块

职责：

- 维护 3 组独立状态
- 保存运行时任务信息
- 管理过期结果丢弃策略

对应目录：

- `app/state/`

## 4. 运行时视角

## 4.1 应用启动

应用启动后完成以下初始化：

1. 读取全局设置
2. 注册托盘和快捷键
3. 初始化状态存储
4. 加载当前启用的 `compiled prompt`
5. 创建必要的 GUI 和 Overlay 控制器

## 4.2 新建选择框

当用户按下 `Ctrl + Shift + Z` 或从 GUI 触发新建时：

1. 进入框选流程
2. 创建一组新的 `GroupConfig`
3. 创建对应的选择框和翻译窗
4. 启动该组的变化巡检

## 4.3 一次翻译刷新链路

对单组来说，一次刷新流程如下：

1. `ChangeDetector` 检测到区域变化
2. `ScreenCaptureService` 获取该区域图像
3. `ImagePreprocessor` 做轻量预处理
4. `OcrEngine` 输出文本
5. `TranslationService` 读取当前 `compiled prompt`
6. `OpenAICompatibleClient` 发起翻译请求
7. 返回结果后，由 Overlay 更新翻译窗

## 4.4 Prompt 编译链路

Prompt 编译不在运行时翻译链路中发生。

它只在配置阶段发生：

1. 用户修改约束层
2. 用户修改知识引用层
3. 用户点击“生成预览”
4. `PromptCompiler` 编译出预览版本
5. 用户确认后，`PromptStorage` 保存 `compiled prompt`
6. 新版本成为运行时默认读取版本

## 5. 数据流设计

## 5.1 组状态数据流

每组至少应维护以下内容：

- 选区坐标
- 翻译窗位置
- 语言对
- 当前 OCR 结果
- 当前翻译结果
- 当前请求版本号
- 是否暂停

## 5.2 Prompt 数据流

Prompt 数据至少包括：

- 固定模板层
- 约束层原始文本
- 知识引用文档路径列表
- 知识提炼结果
- 当前启用的 `compiled prompt`

## 6. 并发模型

推荐采用以下并发原则：

- GUI 绘制与窗口更新在主线程
- OCR 和 AI 请求在后台执行
- 每组独立调度，但共享资源上限

重点是避免以下问题：

- AI 请求阻塞主界面
- OCR 高频运行导致 CPU 飙升
- 旧请求返回后覆盖新状态

## 7. 过期结果控制

由于本项目允许上一条请求继续等待，因此必须有版本控制。

推荐做法：

- 每组翻译任务带上请求序号
- 结果返回时先检查是否仍为该组当前最新版本
- 若不是，则直接丢弃

## 8. Prompt 系统在架构中的位置

Prompt 系统不应被塞进 GUI 或 Translation 模块内部，而应作为独立模块存在。

原因：

- 它有独立的数据结构
- 它有独立的配置流程
- 它有独立的编译与确认机制
- 它的触发时机和运行时翻译不同

因此，架构上必须把 Prompt 系统当作一级模块看待。

## 9. 推荐目录与职责映射

### `app/main.py`

应用主入口。

### `app/app_context.py`

应用级上下文与全局依赖组合点。

### `app/hotkeys.py`

全局快捷键注册与映射。

### `app/settings.py`

全局设置模型与基础配置对象。

### `app/gui/`

设置界面、主窗口、托盘入口。

### `app/overlay/`

选择框、翻译窗、编辑模式控制。

### `app/capture/`

截图服务与变化检测。

### `app/ocr/`

预处理与 OCR 调用。

### `app/prompt/`

三层 Prompt、编译器、存储和数据模型。

### `app/translation/`

AI 接口客户端和翻译服务。

### `app/state/`

多组状态数据模型与运行时存储。

## 10. 第一版边界

第一版架构不做这些复杂化设计：

- 本地服务拆分
- 插件系统
- 多 OCR 引擎热切换
- Prompt 运行时重编译
- 多模态看图翻译主流程

## 11. 结论

这套架构的核心不是“层数多”，而是路径清楚：

- OCR 负责看字
- Prompt 模块负责整理规则
- Translation 负责调 AI
- Overlay 负责展示结果
- State 负责确保多组运行时不混乱

只要这几个职责不互相污染，后面的实现和迭代就会顺很多。
