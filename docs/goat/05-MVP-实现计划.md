# 即时字幕翻译悬浮窗软件 MVP 实现计划

> 面向后续实现阶段使用。本计划的目标不是列愿望，而是明确第一版应该先做什么、后做什么，以及哪些事情先不要做。

**目标：** 做出一个自己会真正长期使用的 Windows 即时辅助翻译工具最小可用版本。

**架构：** 本地桌面应用负责悬浮层、快捷键、截图、OCR 与状态管理；联网 AI 接口负责文本翻译。

**技术栈：** 推荐 Python + PySide6 + 本地 OCR + OpenAI 兼容 API。

---

## 阶段 1：跑通最短主链路

### 目标

先验证最小闭环是否成立：

`创建区域 -> 截图 -> OCR -> AI 翻译 -> 悬浮结果展示`

### 产出要求

- 支持创建 1 组选择框
- 支持固定区域截图
- 支持本地 OCR
- 支持调用 1 个 OpenAI 兼容接口
- 支持一份固定模板层 Prompt
- 支持在选区下方显示翻译窗

### 成功标准

- 手工测试时，能对固定区域完成完整翻译闭环
- 首次可见结果能稳定出现
- GUI 不冻结

### 此阶段不要做

- 3 组并行
- 复杂编辑模式
- 工具条
- 系统托盘细节打磨
- 高级 OCR 优化

## 阶段 2：补齐基础交互

### 目标

把产品从“能跑”提升到“可用”。

### 产出要求

- 支持全局快捷键
- 支持 GUI 基础配置窗口
- 支持系统托盘
- 支持编辑模式切换
- 支持每组源语言和目标语言切换
- 支持暂停、删除、重选区域
- 支持约束层输入和知识引用层文档列表管理

### 成功标准

- 用户可以不改代码完成配置
- 能通过快捷键完成主要操作
- 普通模式与编辑模式切换清晰

## Prompt 系统专项

### 目标

把“提示词输入”升级成“Prompt 编译系统”，避免用户直接维护一整段运行时 Prompt。

### 产出要求

- 固定模板层
- 约束层输入
- 知识引用层输入
- 知识引用层提炼机制
- `compiled prompt` 预览
- 用户确认保存并启用机制
- 本地 `compiled prompt` 文件持久化

### 关键约束

- 固定模板层优先级最高
- 即使用户不填写第二层和第三层，系统也必须可运行
- 知识引用层不得整篇原样注入运行时 Prompt
- Prompt 编译只在配置变更时发生

### 成功标准

- 用户能清楚看到最终实际生效的 Prompt
- 新 Prompt 不会在未经确认的情况下直接影响翻译结果
- 运行时翻译不重复做 Prompt 编译

## 阶段 3：支持 3 组独立工作流

### 目标

从单组原型升级到真正符合需求的多组版本。

### 产出要求

- 最多支持 3 组
- 每组独立保存状态
- 每组独立设置语言对
- 每组有独立翻译窗和视觉标识

### 成功标准

- 3 组互不串状态
- 某一组暂停或删除不影响其他组
- 旧请求不覆盖新请求

## 阶段 4：做稳定性优化

### 目标

把“能用”提升到“更舒服地长期用”。

### 产出要求

- OCR 图像预处理
- 结果去重
- 稳定确认机制
- 基础越界避让
- AI 超时状态反馈

### 成功标准

- 重复字幕不反复闪烁
- OCR 失败时不会频繁输出垃圾结果
- 翻译窗位置不会轻易挡住内容

## 阶段 5：体验打磨

### 目标

把项目从“自己能用”推进到“别人也愿意尝试”。

### 产出要求

- README 完整
- 配置说明清晰
- 默认提示词合理
- 错误提示更友好
- 托盘和 GUI 操作收口

### 成功标准

- 新用户能看 README 跑起来
- 不需要读源码也能理解项目怎么配置

## 功能优先级

## 必做

- Windows 桌面常驻
- 全局快捷键
- 固定区域框选
- 本地 OCR
- 联网 AI 翻译
- 翻译悬浮窗
- 编辑模式
- 3 组独立工作流

## 应做

- 托盘入口
- GUI 配置页
- 越界避让
- 状态提示
- OCR 去重与稳定确认

## 可延后

- 更复杂的提示词模板
- 更多主题样式
- 更精细的布局记忆
- 模型输出清洗增强

## 第一版明确不做

- 自动语言识别
- 历史记录
- 音频转字幕
- 多平台发布
- 本地大模型翻译

## 风险清单

## 风险 1：OCR 稳定性不达预期

### 影响

- 字幕识别错误
- AI 翻译结果失真

### 应对

- 先验证 OCR 在目标场景中的效果
- 尽早加入图像预处理
- 加文本有效性过滤

## 风险 2：AI 延迟不稳定

### 影响

- 超过 4 秒的情况较多
- 用户体验断裂

### 应对

- 选择更快的模型
- 缩短提示词
- 只发必要文本
- 明确 UI 状态提示

## 风险 2.1：Prompt 体系失控

### 影响

- 用户配置后结果不稳定
- Prompt 越来越长
- 很难定位到底是哪一层出了问题

### 应对

- 固定模板层写死
- 约束层与知识引用层分离
- 增加编译预览和确认
- 将知识引用层先提炼再参与编译

## 风险 3：悬浮层交互复杂度过高

### 影响

- 实现周期拉长
- UI 行为不稳定

### 应对

- 第一版坚持“编辑模式 + focus 工具条”路线
- 不做自由拉伸选区
- 不做过多动画与视觉效果

## 风险 4：多组并发状态混乱

### 影响

- 结果串组
- 状态覆盖
- 调试困难

### 应对

- 显式建模每组状态
- 每组请求带唯一标识
- 过期结果严格丢弃

## 建议的近期执行顺序

1. 选定技术栈并创建空项目骨架
2. 先做单组最小闭环
3. 跑通 OCR 与 AI 的时间测试
4. 加入 GUI 配置和快捷键
5. 扩展到 3 组
6. 做稳定性优化
7. 最后整理 README 和开源结构

## Prompt 系统的近期判断标准

不要问“Prompt 配置是不是很灵活”，而要问：

- 用户不写第二层和第三层时，系统还能不能稳定翻译
- 用户能不能看懂最终实际生效的 Prompt
- 新 Prompt 会不会在没确认时误伤运行时结果
- Prompt 编译是否被限制在配置阶段，而不是翻译阶段

---

## 近期判断标准

不要问“功能是不是很多”，而要问：

- 我自己是否会愿意一直开着它
- 它是否比手动切到翻译软件更顺
- 它是否真的减少了打断感
- 它是否在大多数场景下足够快

如果这几个问题的答案是“是”，那这个 MVP 就是成功的。
