# AI 依赖与翻译策略

## 1. 为什么本项目依赖 AI

本项目的目标不是做传统词典工具，而是做一个面向真实使用场景的即时辅助翻译工具。对于中、日、英三语互转，仅靠规则翻译或简单字典替换，很难在不同场景下都保持可读性。

因此，本项目将 AI 作为翻译核心能力使用。

但这里的关键不是“用了 AI”，而是**如何让 AI 以可控、稳定、成本合理的方式参与系统**。

## 2. AI 在系统中的职责

AI 只负责一件事：

- 把 OCR 输出的文本快速翻译成目标语言

AI 不负责：

- 直接看图识别文本
- 解析整段上下文工作流
- 做知识问答
- 做复杂解释或润色

这意味着本项目必须把 AI 的位置放在 OCR 之后，而不是替代 OCR。

## 3. 推荐的整体链路

推荐的默认链路如下：

`屏幕区域 -> 图像预处理 -> 本地 OCR -> 文本清洗 -> AI 翻译 -> 悬浮窗展示`

这样设计的原因：

- OCR 本地做，速度更可控
- AI 只接收纯文本，请求体更小
- 更容易做去重、防抖和结果过期控制
- 相比看图翻译，更容易把大多数场景压缩到 4 秒内

## 4. 为什么不直接让 AI 看图翻译

虽然多模态模型可以直接看图，但本项目不建议第一版这么做。

原因包括：

- 接口耗时通常更高
- 单次成本更高
- 网络波动和服务波动更大
- 不利于稳定控制刷新频率
- OCR 与翻译职责混在一起后，系统更难调优

因此，第一版默认采用“本地 OCR + 文本翻译”的结构。后续如需扩展，可考虑把看图翻译作为特殊兜底模式，而不是主流程。

## 5. AI 接口形态

为降低绑定成本，推荐采用 OpenAI 兼容接口配置方式。

GUI 中至少允许配置：

- Base URL
- API Key
- Model

这样做的好处：

- 可以自由更换服务商
- 可以使用不同速度和成本档位的模型
- 便于用户根据自身网络环境和预算调整

## 6. 模型选择原则

本项目的模型选择优先级应为：

- 响应速度
- 稳定性
- 结果格式可控性
- 成本
- 文学性或润色能力

原因很简单：这不是长文本写作产品，而是实时辅助工具。

因此：

- 不追求最强推理模型
- 不追求长上下文模型
- 优先选响应快、结果稳定的小到中型模型

## 7. Prompt 系统策略

### 7.1 为什么不能只给用户一个大输入框

如果只是给用户一个自由编辑的大 Prompt 输入框，会出现几个问题：

- 用户容易写出互相冲突的要求
- 用户不写内容时，系统 Prompt 可能不完整
- 用户难以表达术语规则、固定表达和风格要求的优先级
- 后续很难调试到底是系统问题还是 Prompt 配置问题

因此，本项目不采用“单段 Prompt 直输”模式，而采用三层 Prompt 架构。

### 7.2 三层 Prompt 架构

本项目的 Prompt 系统由以下三层组成：

- 固定模板层
- 约束层
- 知识引用层

#### 固定模板层

这是系统级固有 Prompt，由程序内置并保持最高优先级。

它负责保证以下内容始终存在：

- 模型角色定义
- 翻译任务边界
- 输出格式要求
- 禁止解释、禁止扩写、禁止分析
- 遇到不完整原文时的保守策略

固定模板层不可被用户删除，也不应被用户直接改写。

#### 约束层

由用户手动输入，主要表达个性化翻译要求，例如：

- 偏直译还是偏自然表达
- 是否保留专有名词原文
- 句式偏好
- 特定术语保留方式

#### 知识引用层

由用户提供本地文档路径，默认以 Markdown 文档为主。

这些文档不是直接整篇塞进运行时 Prompt，而是作为“翻译知识来源”，用于提炼：

- 术语表
- 风格规则
- 固定表达

### 7.3 优先级规则

三层优先级必须写死：

`固定模板层 > 约束层 > 知识引用层`

原因：

- 固定模板层必须确保系统始终完整可用
- 用户约束需要覆盖风格方向，但不能破坏系统底线
- 知识引用层属于辅助知识，不应反向冲掉前两层

### 7.4 为什么固定模板层必须最高优先级

这是整个设计里最关键的约束之一。

如果用户没有填写约束层和知识引用层，系统仍然必须拥有一套完整、稳定、可运行的 Prompt。否则用户只要少填一项，翻译链路就可能失控。

因此：

- 固定模板层必须可单独成立
- 约束层和知识引用层应被视为“可选增强”
- 没有第二层和第三层时，系统依然要能稳定翻译

### 7.5 Prompt 编译机制

真正发给翻译 AI 的，不是原始三层输入，而是 `compiled prompt`。

其生成过程如下：

1. 读取固定模板层
2. 读取用户输入的约束层
3. 读取知识引用层文档
4. 对知识引用层做提炼，转换为术语表、风格规则、固定表达等结构化信息
5. 由专门的 Prompt 整理流程对约束层和知识引用层结果进行归纳与优化
6. 再与固定模板层拼接，生成最终 `compiled prompt`

### 7.6 是否让 AI 参与 Prompt 编译

你的设想是对的：第二层和第三层可以先经过 AI 理解和优化，再与第一层拼接。

但这里必须加一个工程约束：

- Prompt 编译只在配置变更时发生
- 绝不能在每次字幕翻译时重新做一次 Prompt 编译

否则会直接破坏 4 秒内出结果的目标。

### 7.7 Prompt 编译触发时机

推荐触发时机如下：

- 用户修改约束层内容
- 用户增删知识引用文档
- 用户手动点击“生成预览”

运行时翻译阶段不触发 Prompt 编译。

### 7.8 用户确认机制

在 Prompt 系统中，用户不应在无感知的情况下直接启用新 Prompt。

推荐流程如下：

1. 用户修改约束层和知识引用层
2. 用户点击“生成预览”
3. 系统执行 Prompt 编译
4. GUI 展示 `compiled prompt` 预览
5. 用户点击“确认保存并启用”
6. 系统将 `compiled prompt` 保存到本地文件，并将其设为当前运行版本

这样做的好处：

- 用户可以看到最终实际生效的 Prompt
- 出现问题时更容易定位
- 不会因为一次误编辑直接污染运行时翻译结果

### 7.9 本地文件保存策略

`compiled prompt` 必须以文件形式保存在用户本地电脑中。

这样做有几个作用：

- 运行时直接读取已确认版本，降低重复构建开销
- 便于用户回看和调试
- 为后续版本管理、导出和回滚留接口

### 7.10 Prompt 原则

即使引入三层架构，最终 Prompt 仍应保持以下特征：

- 短
- 硬
- 可控
- 面向翻译任务

它应明确约束模型：

- 只输出翻译
- 不加解释
- 不做分析
- 不加多余前后缀
- 尽量保留原句结构和语气

## 8. 请求与响应策略

### 8.1 单条请求输入

每次只发送当前 OCR 文本与当前启用的 `compiled prompt`，不发送整段历史。

原因：

- 降低延迟
- 降低提示词复杂度
- 降低模型输出失控概率

### 8.2 单条请求输出

响应应只包含翻译文本。

不允许返回：

- “翻译如下：”
- 注释说明
- 多候选结果
- 分析性描述

## 9. 任务调度策略

AI 请求层需要和 OCR 层配合，避免以下问题：

- 同一句 OCR 重复请求
- 新文本来了，旧请求还在排队
- 旧结果回来后覆盖新结果

因此推荐策略如下：

- OCR 去重后再发 AI
- 每组只保留“当前进行中请求 + 最新待处理文本”
- 旧结果若已过期则丢弃
- 超过 4 秒继续等待，但 UI 要显示状态

## 10. 错误与降级策略

### 10.1 OCR 结果质量差

若 OCR 结果明显无效，则不发 AI，请继续等待下一次稳定结果。

### 10.2 AI 接口超时或失败

若 AI 请求失败：

- 保留上一条翻译
- 在 UI 显示“翻译失败”或“翻译中断”
- 不清空当前窗口内容

### 10.3 模型输出异常

若模型返回解释性文本或非预期格式：

- 先做轻量结果清洗
- 若仍不满足要求，再标记为异常结果

## 11. 后续扩展方向

如果未来项目稳定后，可扩展以下 AI 能力：

- 术语保持
- 轻量上下文记忆
- 用户自定义翻译风格
- 指定领域提示词模板
- OCR 低置信度时的多模态兜底

但这些都不应进入第一版主流程。

## 12. 结论

本项目依赖 AI，但必须是“可控依赖”。

也就是说：

- AI 是翻译引擎，不是系统主控
- AI 只接纯文本，不接主流程图像识别
- AI 要快、稳、可替换
- Prompt 要先经过分层、编译和用户确认，再进入运行时
- 文档、配置和代码结构都要围绕这个前提设计
