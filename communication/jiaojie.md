## 项目概述

一个 Windows 桌面即时翻译悬浮窗工具。用户用鼠标框选屏幕上的字幕区域，软件持续 OCR 识别该区域的文字变化，调用 AI 翻译，结果显示在悬浮窗中。最多支持 3 组独立的框选+翻译工作流。

## 当前技术栈

Python 3.9 + PySide6 + PaddleOCR 2.7.3 + OpenAI 兼容 API

## 核心架构链路

框选区域 → 每500ms截图 → BLAKE2b变化检测 → OCR（PaddleOCR+Tesseract兜底） → AI翻译 → 悬浮窗展示

## 当前核心矛盾

1. 翻译质量与速度无法兼得——flash模型关思考 1 秒出结果但不服从复杂约束（如"只输出平假名"），开思考 5-26 秒太慢
2. 每次都重新发送完整规则（200-1600字），模型重复消化
3. 缺乏上下文记忆，同一会话中的术语一致性靠 prompt 硬撑

## 我们讨论的方向

**Agent 化改造**：把 TranslationService 从无状态管道升级为有记忆、能自主决策的在线翻译助手。规则只在会话建立时消化一次（用 thinking 模型，慢一次），后续翻译只发原文（秒回）。上下文存本地，窗口满时 compact 压缩。

**翻译模板**：把语言方向、提示词配置、会话管理合并为一个"翻译模板"，一个模板=一个完整翻译场景。

**待验证**：DeepSeek API 是否支持同一条 messages 里混用 thinking enabled/disabled。

## 二次思考（读完 react.md 和 huifu.md 后）

### 对第一次反馈的修正

看到你们的回应后，我承认有几个地方理解偏了：

**1. compact 压缩不一定要调 API**
我说"压缩算法需要调 API"是错的。你们说的纯客户端操作（术语 KV + 最近 N 轮 + 旧摘要文本拼接）更合理。我当时想的是用 LLM 生成摘要，但这确实多余了。

**2. "不关 thinking"的替代方案不成立**
你们指出这个方案"不能解决慢的问题"——完全正确。我提这个是因为担心 thinking 切换不可靠，想给个备选方案，但确实没抓住核心矛盾。

**3. 两个独立 Agent 是多余的**
同意。规则消化和翻译执行是同一会话的两个阶段，不需要拆成两个 Agent。

### 需要强调的关键点

**POC 验证时必须测的三件事**：
1. `reasoning_content` 是否真的能被后续非 thinking 轮读到
2. thinking tokens 计费 — 消化一次规则消耗多少 tokens？成本能否接受？
3. KV cache 命中率 — thinking 切换是否导致 cache miss，影响延迟

**OCR 卡死定位的补充**：
如果日志显示 OCR-OUT 有输出但翻译窗不更新，还需要检查：
- `TranslationService` 的去重逻辑是否误杀了新文本
- Signal 回主线程的队列是否阻塞
- 翻译窗的 `setText()` 是否被其他操作锁住

**编辑模式闪烁的根本原因**：
不只是 `apply_model` 的问题，还要检查 `_upsert_selection_box` 的调用频率。如果每 500ms 都调用，即使加了状态比对，仍会有 CPU 开销。建议在变化检测层加过滤：只有 OCR 文本真正变化时才触发 `_upsert_selection_box`。

### 你们采纳的方案我补充几点

**状态比对方案 A**：
除了 `(geometry, group_id, lang_pair)`，还要比对 `edit_mode` 状态。否则进入/退出编辑模式时可能不触发重绘。

**✓/✗ 快速反馈按钮**：
建议做成半透明悬浮在翻译窗右上角，鼠标移入才完全显示。避免遮挡翻译内容。

**大段文本去重只对比尾部 200 字**：
这个阈值需要实测调优。如果用户框选的是代码或日志（变化在中间而非尾部），可能误判。建议加个 fallback：相似度 >0.95 且长度变化 <5% 才跳过。

### 最终建议

你们的优先级判断是对的：
```
🔴 闪烁 > OCR诊断 > thinking验证
🟢 Agent开发 > GUI重构
```

但我建议在修闪烁时，**同时做 OCR 日志**（改动很小，加 3 行代码）。这样能并行收集数据，不用等闪烁修完再诊断 OCR。

另外，**翻译方向持久化**（问题 6）虽然是小问题，但修复成本极低（5 行代码），建议和闪烁一起顺手修掉。
